# Project Retrospective

## Milestone: v1.1 — Web Playground

**Shipped:** 2026-09-20
**Phases:** 6 | **Plans:** 39

### What Was Built

A SolidJS GitHub Pages playground that runs six native Rust/WASM scenes with hash URLs, catalog previews, honest Reset labels, pointer interaction, and automatic main-push delivery.

### What Worked

- Shipping a thin hosted Dam Break slice in Phase 17, then expanding scenes, made Pages delivery real before the catalog was complete.
- Independent AI review bound to exact digests kept phase gates honest without blocking hobby pace.
- A stale milestone audit plus gap-closure phases 20–21 recovered UI fidelity instead of archiving known chrome lies.

### What Was Inefficient

- Post-Phase-18 responsive-shell work undid in-app previews and Reset label honesty, requiring a later audit and two extra phases.
- GSD summary `---` body rules can hide provenance frontmatter from the lifecycle parser.
- Plan one-liners dumped wholesale into MILESTONES.md until curated down to a v1.0-style record.

### Patterns Established

- Product smoke is `just web-player-smoke`; Phase 16 `just web-smoke` stays opt-in forensic chrome.
- Playground WASM stays a private crate; `liquidfun` remains the sole default member.
- Planning archive is not a git release tag.

### Key Lessons

1. Re-audit after gap-closure phases; do not complete a milestone on a stale `tech_debt` audit.
1. Keep empty-hash Dam Break replacement and unknown-hash fallback as distinct useful states.
1. File-length debt on integration-test crate roots needs `foo.rs` plus `foo/` with `#[path]`, not a checker exception.

### Cost Observations

- Model mix: unavailable; no estimates asserted.
- Sessions: multiple discuss/plan/execute/audit turns across 16–21.
- Notable: v1.1 stayed much smaller than v1.0 (39 plans vs 252).

## v1.0 — Experimental Foundation

**Archived:** 2026-09-17. **Phases:** 16. **Active plans:** 252. This milestone was not a package release.

### What was built

Native rigid/particle physics, upstream comparison and replay tooling, private examples/testbed, packaged-consumer isolation, and a practical experimental preparation checklist.

### What worked

- Native consumer isolation, focused regression fixtures and independent review preserved useful confidence.
- Explicitly separating current implementation results from historical strict evidence kept claims honest.
- Archiving superseded plans prevented accidental execution of retired certification work.

### What was inefficient

The original production-quality certification goal accumulated expensive cross-platform campaigns, controlled-host prerequisites and repeated evidence work beyond the owner's hobby needs. Stale generated planning status also required targeted corrections.

### Patterns to retain

Local checks plus one convenient CI job; expensive tools available manually; small source-identified results with honest limitations; preserve failed evidence; review proportional to changed behavior.

### Lessons

1. Revisit the desired quality level before investing in certification infrastructure.
1. Preserve useful tools without turning every possible check into a completion gate.
1. Distinguish implementation completion, experimental package preparation and actual publication.
1. Validate derived planning state after CLI updates rather than assuming generated fields are accurate.

### Cost observations

Session counts, model mix and token/currency totals are unavailable; no estimates are asserted. Future milestones should be much smaller and centered on concrete use.
