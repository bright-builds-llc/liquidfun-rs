# Phase 13.1 Aggregate Execution Contract

This file is the only supported execution route for Phase 13.1. The standard
per-plan `execute-plan.md` route is intentionally not used: its task/plan commit
and summary behavior conflicts with the repository rule that all Rust
pre-commit gates must pass before any source commit.

## Orchestration

The execute-phase orchestrator must use Pattern-B task-only agent semantics.
Each plan is a bounded sequential segment, not an independently committed plan:

1. Run Plans 01 through 14 in wave order in the same detached aggregate
   worktree.
1. For every segment, explicitly prohibit staging, commits, summaries, STATE,
   ROADMAP, lifecycle, or other planning writes. The task agent returns its
   result to the orchestrator without invoking standard summary or commit
   behavior.
1. Keep progress and evidence only below
   `/tmp/liquidfun-rs-phase13.1/segments/13.1-NN/`. The next segment reads that
   external evidence and the live aggregate worktree, never a prior SUMMARY.
1. Treat Plans 01 through 14 plus Plan 15 Tasks 1 and 2 as one aggregate source
   candidate. Only the orchestrator, after every Plan 15 verification gate is
   green on the unchanged candidate, may execute Plan 15 Task 3 and create the
   single source commit.
1. After fast-forward integration, verify the original baseline manifest
   exactly before writing any planning artifact. Only then create all 15
   summaries and authorized lifecycle/STATE/ROADMAP documents together, audit
   and stage that set separately, rerun the required docs/lifecycle checks, and
   create one separate docs commit.

No segment agent may invoke the standard per-task or per-plan commit path. A
failed segment leaves the candidate uncommitted and preserves its external
evidence for diagnosis.

## External Segment Evidence

Each segment writes one machine-readable
`/tmp/liquidfun-rs-phase13.1/segments/13.1-NN/evidence.json` containing:

- plan and task identifiers;
- aggregate base HEAD and current candidate digest;
- exact commands, exit statuses, and output artifact digests;
- changed tracked and untracked path inventories;
- verification results and residual risks;
- `staged: false`, `commits: []`, and `summary_written: false`.

The orchestrator records segment completion externally. It must not update
tracked or untracked planning files in the original worktree during segment
execution, so Plan 01's exact baseline remains unchanged through source
fast-forward and its immediate post-fast-forward verification.

## Cumulative Candidate Snapshot

At the end of every implementation segment, refresh
`/tmp/liquidfun-rs-phase13.1/segments/13.1-NN/candidate/` from the aggregate
worktree:

1. Write `tracked.patch` using `git diff --binary --full-index` against the
   preserved base HEAD.
1. Enumerate every untracked candidate file with a NUL-delimited Git path
   source. Reject absolute paths, `..` traversal, and any path from the original
   preservation manifest or paused Phase 14 set.
1. Write `untracked-manifest.json` with the encoded repo-relative path, Unix
   mode, byte size, and SHA-256 of every untracked file in deterministic
   bytewise path order.
1. Create `untracked.tar` from exactly that ordered NUL-safe path list, preserving
   file modes and contents. Record its SHA-256 and verify a fresh archive listing
   equals the manifest path set.
1. Write `candidate-tree-manifest.json` for every tracked or untracked candidate
   path with encoded path, mode, size, SHA-256, and tracked/untracked kind in
   deterministic order. Record the SHA-256 of this manifest.
1. Write `snapshot.json` containing the base HEAD, segment ID, tracked patch
   SHA-256, untracked manifest SHA-256, untracked archive SHA-256, candidate-tree
   manifest SHA-256, counts, and the prior segment snapshot digest.

Recovery is valid only when the tracked patch, untracked manifest/archive, and
candidate-tree manifest all verify. A tracked diff alone is never a cumulative
snapshot.

## Cargo-Only Reconstruction

Plan 15 creates a clean detached Cargo-only worktree at the preserved base,
applies `tracked.patch`, and extracts `untracked.tar` only after validating every
archive entry against `untracked-manifest.json`. It then recomputes the complete
candidate-tree manifest using the same path encoding, ordering, modes, sizes,
and SHA-256 rules. The reconstructed manifest bytes and digest must equal the
aggregate worktree's final candidate-tree manifest before any Cargo-only test
runs.

## Commit and Lifecycle Boundary

Plan 15 is the sole source-commit authority:

- no staging or source commit before the complete final matrix is green;
- exactly one reviewed structural source commit;
- manifest-guarded fast-forward into the original main branch;
- exact original porcelain and tracked/untracked baseline verification
  immediately before and after fast-forward;
- no Phase 14 source path changes.

After that post-fast-forward baseline proof, the orchestrator creates all
`13.1-01-SUMMARY.md` through `13.1-15-SUMMARY.md` and the required lifecycle,
STATE, and ROADMAP updates as one explicitly authorized post-integration set.
The allowed docs-commit paths are `.planning/ROADMAP.md`, `.planning/STATE.md`,
the phase's 15 plans, 15 summaries, `13.1-CONTEXT.md`,
`13.1-DISCUSSION-LOG.md`, and `13.1-EXECUTION.md`; no other path is authorized.

Before creating the docs commit, the orchestrator must run the repository's
mandatory Rust gate again, in order: `cargo fmt --all`,
`cargo clippy --all-targets --all-features -- -D warnings`,
`cargo build --all-targets --all-features`, and
`cargo test --all-features`. It then runs the Bright checker, Markdown check,
all 15 summary-schema validations, and lifecycle validation with plans
required. The green evidence is bound to the staged-tree digest.

The orchestrator reviews and stages only the allowlisted docs set and creates
one separate docs commit containing no source files. It records `docs_sha` and
proves that the docs commit's sole parent is `source_sha`, final `main` equals
`docs_sha`, its committed path set is entirely allowlisted, all 15 summaries
validate, and the phase lifecycle remains valid.
