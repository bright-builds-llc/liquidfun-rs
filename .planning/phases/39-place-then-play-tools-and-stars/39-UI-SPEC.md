### Tool overlay (canvas, world space) [UI-D13]

Drawn by `drawPuzzleTools(context, camera, tools)` in `render/puzzle-tools.ts`, on the 2D canvas after the scene frame and **before** `drawGlassCup` (D-22 order: particles → tools → glass). Inside `save()` / `try` / `finally { restore() }`. Geometry is the inspector outline quad (D-02), projected with `projectPoint`. Line widths are fixed CSS pixels at every camera scale.

In shaded-blob mode the WebGL water sits under the transparent 2D canvas, so the same draw lands above the water in every render mode. Walls arrive as thin `#94A3B8` `rigidSegments` lines. Tools are filled solids with a dark keyline, so they read as the player's pieces against walls, the dark background and the bright blue water. While running, the plank's own `rigidSegments` outline lies exactly under the overlay quad and is covered.

Per tool, draw these passes in order:

| Pass | Normal (building, valid) | Selected | Invalid | Locked (running, ended) |
|------|--------------------------|----------|---------|-------------------------|
| 1 Halo | none | stroke `rgba(244, 247, 250, 0.40)`, width 8 | none (selected + invalid: same halo as selected) | none |
| 2 Keyline | stroke `rgba(7, 16, 24, 0.80)`, width 4 | same | same | same |
| 3 Fill | `rgba(51, 65, 85, 0.92)` (`#334155`, the existing rigid fill) | same as normal | `rgba(90, 36, 48, 0.92)` (`#5A2430`) | same as normal |
| 4 Stroke | `#CBD5E1` (existing rigid stroke), width 2, solid | `#F4F7FA`, width 2, solid | `#F07178`, width 2, `setLineDash([6, 4])` | `#CBD5E1`, width 2, solid |

- `lineJoin: "round"`. Reset `setLineDash([])` after each invalid tool. `restore()` must leave `lineDash`, `globalAlpha`, `lineWidth`, `strokeStyle` and `fillStyle` unchanged.
- Invalid uses a dash as well as red, so the state does not rely on hue. Red on the blue water is separated by the dark keyline.
- Locked tools are undimmed and identical to normal (D-22). No tool is ever invalid while running.
- While a tool is dragged, it is drawn at its live snapped pose with the selected style (plus the invalid style if the latest inspection says so). There is no second ghost at the old pose.
- Tools without a geometric status (unknown kind, angle, out of range) are not drawn (the outline lane is zeros).
- The glass cup gains a `★ Brim` tick through the Phase 38 tick list (`goalTicks` appends `{fraction: brimCount / fullCount, label: "★ Brim"}`); `drawGlassCup` is not changed.

## Component Contracts

### Tool tray (D-17, TOOL-01)

- Leaf `div.puzzle-tray` with `data-hud-obstacle`, `role="group"`, `aria-label="Tools"`. The leaf itself is a transparent container with no chip surface; its items are the buttons.
- One `button.product-control.puzzle-tray-item` per tool kind from `levelInfo()` (`toolKinds` / `toolCounts`), in `levelInfo` order. Items share the tray width equally with 8 px gaps in every layout (two landscape items are 64×44 each). Item height is 44 and width at least 44.
- Capacity per fixed box: landscape 2 kinds, portrait and form-factor 3 kinds. A level with more kinds is a Phase 40 layout change.
- Item content: Plank icon (22 px) + 4 px + kind name ("Plank") + flexible space + count. The name is shown when the item is at least 96 px wide (landscape with 1 kind; portrait and form-factor with up to 2 kinds); otherwise icon + count only, and the name stays in the accessible name and `title`.
- Count text `×2` (remaining = budget − placed of that kind), tabular, `#F4F7FA`; `×0` is `#A9B4C0`.
- States:
  - default: `.product-control` colors (`#151D28`, border `#2A3441`, text `#F4F7FA`).
  - armed: `aria-pressed="true"`, background `#1C2734`, `box-shadow: inset 0 0 0 2px #F4F7FA` (white editing highlight).
  - unavailable (remaining 0, or phase is not `building`): `aria-disabled="true"`, Phase 38 disabled look (`#A9B4C0` on `#151D28`), clicks ignored, never native `disabled`, so focus survives the last Enter-placement.
- Mouse or tap: arms the kind; pressing an armed item disarms it (D-17). Space on a focused item does the same as a click.
- Enter on a focused item places one tool at the build-area centre, snapped, angle index 0, and selects it, without arming (D-23). The keydown handler calls `preventDefault` so the native click does not also arm.
- e2e hooks: `data-tool-kind="plank"`, `data-remaining="2"`.

### Selection bar (D-19, TOOL-02)

- Leaf `div.puzzle-selection-bar` with `data-hud-obstacle`, `role="toolbar"`, `aria-label="Selected tool"`, `aria-orientation="horizontal"`. Mounted for the whole route.
- Three `button.hud-button`-sized (44×44) icon buttons using `.product-control` colors, in this order:
  1. Rotate counterclockwise: +15° (angle index +1 mod 24).
  1. Rotate clockwise: −15° (angle index −1 mod 24).
  1. Remove: deletes the selected tool. Selection then clears, and focus stays on the Remove button (now `aria-disabled`).
- Enabled only in `building` with a selected tool; otherwise every button is `aria-disabled="true"` with the disabled look. Rotation does not snap back or block when the result is invalid (D-20).
- Each button has `title` equal to its accessible name.

### Fill meter (extends Phase 38 D-11)

- Ticks: `★ Win` (0.6), `★ Brim` (`brimCount / fullCount`, 0.9 for first-pour), `Full` (1.0). Brim is a ★ tick (amber).
- **Reached ticks:** a ★ tick whose latch has happened in the current run (Win at the win latch, Brim at the Brim latch) gets `data-reached="true"` and `box-shadow: 0 0 0 2px rgb(230 195 92 / 40%)`. Building ticks never have the halo, so the Phase 38 look is unchanged there. This is how "the fill meter lights its Win tick" (D-10).
- Values: `building` 0%; `running` (including Filled in-progress) live `floorPercent(goalCount)`; `ended` won: **frozen at the peak-held %** read at the decided step (90% for the reference); `ended` lost: frozen at the Phase 38 latch value **[UI-D16]**. The meter may drop from the live value to peak-held at the decision step (920 → 811 counts, 100% → 90%), so the meter and the card always agree once the run is decided.
- `aria-valuetext` keeps the Phase 38 form: "90% full, target 60%".

### Timer (extends Phase 38 D-09)

- `running` counts down per presented frame through the Filled in-progress state and **freezes at the decided step** **[UI-D16]**: won with Brim → remaining at the Brim latch (`0:07.6` for the reference at step 262); won without Brim and lost → `0:00.0`. The timer is step-based, so it is identical at 1×, 2× and 4×.

### Canvas editor (D-17, D-18, D-20, D-23)

- The puzzle `canvas.scene-canvas` becomes focusable: `tabindex="0"`, `role="application"` (replaces `img`, so screen readers pass keys through to the editor), and the Phase 38 `aria-label` text unchanged. It also gets `aria-describedby="puzzle-keyboard-help"`, a `.visually-hidden` paragraph in the panel **[UI-D17]**. If a Phase 38 test queries `role="img"`, update it and list the change in the SUMMARY.
- `touch-action: none` on the puzzle canvas, so drags never scroll or zoom the page.
- Cursor classes (puzzle-specific, never `canvas-interactive`, Research Pitfall 6): `.puzzle-canvas--armed` → `cursor: copy`; `.puzzle-canvas--over-tool` (mouse hover in building) → `grab`; `.puzzle-canvas--dragging` → `grabbing`; otherwise `default`.
- Pointer rules in `building` only:
  - Armed + tap or click anywhere on the canvas: place at the snapped point, angle index 0, select it, disarm. This happens even over an existing tool; the overlap then shows as invalid.
  - Not armed + press on a tool (distance ≤ 22 CSS px slop; nearest wins; ties go to the selected tool, then the highest id): select it. Moving past the drag threshold starts a drag that keeps the grab offset and snaps live to the 0.05 m grid. Touch drags draw and snap the tool 48 CSS px above the finger. Tap-to-place never lifts (Research Pitfall 9).
  - Not armed + tap on empty canvas: deselect.
  - Release never snaps back (D-20).
- Outside `building` the canvas ignores editor input, and the tools are drawn locked.
- Keys while the canvas or any puzzle HUD control has focus (D-23; ignored when the event target is a `button`, `select`, `a` or `input` for Space and Enter, and ignored while the options drawer is open):

| Key | Action (building only unless noted) |
|-----|-------------------------------------|
| Arrow keys | nudge the selected tool 1 cell (0.05 m) |
| Shift + Arrow | nudge 10 cells |
| R / Shift+R | rotate +15° / −15° |
| Delete, Backspace | remove the selected tool |
| Space | Play in building (when enabled), Stop in running; no-op in ended and loading |
| Escape | deselect and disarm |

A `.visually-hidden` `div#puzzle-editor-status` with `aria-live="polite"` and `aria-atomic="true"`, inside the panel and not a HUD leaf. It announces committed editor events only (copy below). Nudges announce only when validity changes.

Transitions:

- Play: building → running on a fresh run session built from canonical placements. Any selection and armed kind are cleared.
- Stop: running → building on a fresh no-placement preview session with placements kept. Latched stars are recorded (D-15). Focus stays on the Play/Stop button.
- Decision: running → ended at `decidedStep` (D-10), then the 120-step settle tail and held frame (Phase 38).
- Retry, Edit and route change are unchanged from Phase 38.
- Focus (extends UI-D8): entering `building` from Stop or Edit focuses Play/Stop only if focus was on a control that became disabled. Entering `ended` focuses the primary result action. Removing the selected tool from the selection bar keeps focus on Remove. Never move focus that is outside the panel.
- No HUD leaf mounts, unmounts or resizes on any transition. There are no CSS transitions or animations on puzzle chrome or the overlay.

## Accessibility Contract

- **Targets:** every tray item, selection-bar button and transport button is at least 44×44 CSS px. Every tool's hit area is at least 44 px across through the 22 px slop.
- **Focus order (DOM order):** site-header trigger → canvas build area → tray items → selection bar (rotate counterclockwise, rotate clockwise, Remove) → transport (Play/Stop, Speed, Clear) → result actions (ended only) → options trigger. Visual positions differ by layout; DOM order is fixed.
- **Disabled semantics:** all new controls use `aria-disabled="true"` (focus stays), never native `disabled`. The disabled Next from Phase 38 is unchanged.
- **Live regions:** the result message (polite, atomic; committed edits only), `#puzzle-editor-status` (polite), and the failure heading (assertive). The meter and timer stay non-live.
- **Names contain visible text** (WCAG 2.5.3): "Clear all tools" contains "Clear", "Plank, 2 left" contains "Plank", and "Speed 2×" contains "2×".
- **Non-color cues:** invalid tools are dashed as well as red; star states carry hidden text; armed uses `aria-pressed`.
- **Contrast:** `#F07178` status text on `rgb(21 29 40 / 86%)` over `#071018` is above 4.5:1 at 14 px and larger. The keyline separates tool strokes from both the dark background and the `#4DA3FF` water.
- **Reduced motion:** no animation exists. The drag lift is an instantaneous offset, and fast-forward is user-chosen.
- **Keyboard:** full parity for place, select, nudge, rotate, remove, play and stop (TOOL-06), without focus traps.
